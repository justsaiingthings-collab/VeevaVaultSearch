Getting Started

What is VaultSearch?

VaultSearch is a structured search and retrieval layer built directly on top of Veeva Vault. It is not AI-powered. Instead, it uses deterministic VQL (Veeva Query Language) templates that map plain-English search intent to audit-compliant queries.

VaultSearch was built for the 80% use case: QA managers looking for approved SOPs before an inspection, Regulatory Affairs finding documents in specific lifecycle states, Clinical Ops retrieving deviation-CAPA linkages, and Validation Engineers auditing compliance packages. It runs completely within your Veeva Vault instance—no data egress, no cloud processing, and every search is logged for inspection readiness.

Key principle: You always see the exact VQL being executed. This is not a black box. If you need to explain a search result to an auditor, the VQL panel shows precisely what ran and why.

Requirements

Veeva Vault Instance
You must have a running Veeva Vault account (sandbox or production). VaultSearch connects to your instance over HTTPS.
API Version 19.1+
Your Vault instance must be on API version 19.1 or later. This requirement enables all VQL template features. Contact your Vault Administrator if unsure of your version.
User Account with Document Permissions
You need an active Vault user account with read access to the document types you intend to query. VaultSearch respects Vault's own Access Control List (ACL)—if you cannot access a document in the native Vault UI, VaultSearch will not return it either.
Supported Browsers
VaultSearch works on modern browsers: Chrome, Firefox, Safari, or Edge (latest two versions). Mobile browsers (iOS Safari, Chrome Mobile) are supported but optimized for desktop use.

Opening for the First Time

When you first open VaultSearch (or on a new browser), you will be taken to the connect.html page:

  1. Enter your Vault domain. This is the base URL of your Vault instance (e.g., acme.veevavault.com). See "Connecting to Vault" section below for details.
  2. Choose authentication method: Username/Password or OAuth 2.0.
  3. Grant permission or enter credentials. You will not be asked for sensitive data a second time in the same browser session.
  4. Redirected to the search panel. Once authenticated, you will see the main VaultSearch interface with the search bar, suggested chips, and filters sidebar.

Your session is tab-scoped. Closing the tab ends your session. Opening VaultSearch in a new tab requires re-authentication.

Connecting to Vault

Username & Password Authentication

Username/Password auth uses Vault's native credentials. Follow these steps:

1
Enter your Vault domain
This is the base URL where you log into Vault normally. Example: acme.veevavault.com (without https:// prefix—VaultSearch adds that automatically). If you use a Veeva-hosted instance (not white-labeled), it usually follows the pattern {tenant}.veevavault.com.
2
Select "Username & Password"
Enter your Vault username (usually an email) and password. These credentials are used only to obtain a session token from Vault's OAuth endpoint.
3
Understand the session token
A session token is a temporary credential issued by Vault. It grants you access to the API for the duration of your session (typically 1–8 hours, depending on your Vault configuration). Tokens are not persisted—they exist only in your browser's sessionStorage for the duration of the tab. Closing the tab or logging out clears it.
4
You're authenticated
The token is validated. You can now search. If the token expires during a search, you will see "Session expired" and will need to reconnect via the connect page.
Password security: Your password is transmitted directly to Vault over HTTPS, not through VaultSearch. VaultSearch never sees or stores your password.

OAuth 2.0 Setup

OAuth 2.0 is the recommended method for production use. It does not require sharing your password with VaultSearch. Instead, you authorize the VaultSearch application once, and it can request tokens on your behalf.

What is an "Application Client ID"?

An Application Client ID is a unique identifier for the VaultSearch application within your Vault instance. Your Vault Administrator registers VaultSearch as an OAuth 2.0 application, which generates a Client ID. This ID is public and safe to share (it is not a secret or password).

Finding the Client ID in Vault Admin

  1. Log into your Vault instance as an Administrator.
  2. Go to Admin > Security > OAuth 2.0 Applications.
  3. Find the row for "VaultSearch" (or the name your team registered).
  4. Copy the Client ID value (a long alphanumeric string).
  5. Paste it into the OAuth field on VaultSearch's connect page.

Auto-detect vs. Manual Entry

VaultSearch will attempt to auto-detect the Client ID from your Vault domain. If auto-detect succeeds, the field will be pre-filled. If it fails (e.g., your Vault uses a custom domain or SSO), you may enter it manually. Your Administrator can provide the correct value.

First-Time OAuth Grant

The first time you use OAuth with VaultSearch, you will be redirected to your Vault instance to approve the request. You will see a screen asking you to grant VaultSearch permission to "Read documents" and "Access your profile." Click "Approve" to continue. This approval is one-time; subsequent logins will not require re-approval.

Permission scope: VaultSearch requests read-only access. It cannot modify, delete, or create documents.

Saving Connections

VaultSearch can optionally remember your Vault domain and authentication method across browser sessions. However, sensitive data is never saved:

  • What gets saved: Vault domain, authentication method (Username/Password or OAuth), and the name of the cached connection.
  • What never gets saved: Passwords, session tokens, Client IDs, or any other credentials.

If you check "Remember this connection" on the connect page, VaultSearch will show it as a quick-select option the next time you open the page. Selecting it will still require you to re-authenticate (enter password or re-approve OAuth), but you won't have to type the domain again.

You can delete saved connections at any time via the "Manage connections" link on the connect page.

Troubleshooting Connection Errors

Domain not found / Invalid domain

Symptom: "Unable to resolve Vault domain" error.

Cause: You may have entered an incorrect domain or URL format.

Solution: Double-check the domain. It should be just the host name (e.g., acme.veevavault.com), not a full URL (https://...). Ask your Administrator for the correct Vault domain if unsure.

Wrong credentials / Authentication failed

Symptom: "Invalid username or password" or OAuth approval fails.

Cause: Incorrect credentials, expired password, or account deactivation.

Solution: Verify your username and password are correct. If you recently changed your password in Vault, use the new one. If the error persists, contact your Vault Administrator.

SSO not configured

Symptom: OAuth redirects to an SSO login page, then fails.

Cause: Your Vault instance uses Single Sign-On (SAML, Okta, Azure AD, etc.), and the OAuth application may not be registered with your SSO provider.

Solution: Contact your Vault Administrator. They may need to update the OAuth application's Redirect URI in both Vault and your SSO provider.

VPN / Network connectivity

Symptom: "Connection timeout" or "Cannot reach Vault."

Cause: Your Vault instance may be on a private network (intranet) and unreachable from outside.

Solution: Ensure you are on the correct network (corporate VPN, office network, etc.). Test by opening Vault in a browser directly. If that works, VaultSearch should work too.

Using the Search Panel

The Search Bar

The search bar is the central input field where you type or paste your query. It understands plain-English keywords and maps them to VQL templates.

Examples of recognized keywords

  • "approved SOPs" → Template: SOP_Approved
  • "open deviations" → Template: Deviation_Open
  • "overdue CAPAs" → Template: CAPA_Overdue
  • "audit-ready documents" → Template: Audit_Package_Ready
  • "documents expiring this quarter" → Template: Document_Expiry_Soon

How the parser works

The parser is deterministic and rule-based. It tokenizes your input, looks for keywords from a predefined set, and selects the best-matching template. If no exact match is found, it returns the most likely candidates as suggested chips. The parser does not use machine learning and will always return the same result for the same input.

Refining results

After you initiate a search, use the Filters sidebar (described below) to narrow results by lifecycle state, document type, severity, date range, and more. Filters apply after the VQL executes and refine the results in real-time without requiring a new query.

Suggested Query Chips

Below the search bar, you will see a row of suggested query chips. These are pre-built templates tailored to your role. Clicking a chip is equivalent to typing that query and pressing Enter.

Role-based suggestions

The chips you see depend on your role. For example, QA Admin sees: "Approved SOPs," "Open Deviations," "CAPA Overdue," "Audit Package."

How to use them

Click any chip to execute that query immediately. Results will appear below. You can then use the filters sidebar to refine further.

Filters Sidebar

The filters sidebar allows you to refine search results without re-running the VQL. All filters persist in the session.

Available filters

Lifecycle State
Filter by document status: Approved, Effective, Archived, Draft, Superseded, etc.
Document Type
Narrow to specific document types: SOP, Deviation, CAPA, Risk Assessment, Change Notice, etc.
Severity
For deviations and incidents, filter by severity level: Critical, High, Medium, Low.
Date Range
Filter by creation or modification date.
Expiration Status
For documents with expiration dates, filter by "Not Yet Expired," "Expires Soon (30 days)," or "Expired."

Applying filters

Filters are applied immediately when selected. If a filter combination returns zero results, you will be notified. You can then adjust or clear filters to broaden the results.

Filter persistence: Filters persist throughout your session. Closing the tab clears all filters.

Version Grouping

By default, VaultSearch returns only the latest version of each document. Historical versions are hidden to reduce clutter.

Why latest versions only?

In compliance scenarios, you almost always want the current approved version. Older versions are archived for historical reference but are not relevant to most day-to-day queries.

Expanding version history

To see all versions of a document, click the "Show versions" link or arrow next to the document title. This will expand a collapsible section showing all versions with lifecycle state and modification date for each.

The VQL Panel

Every search result includes a VQL panel at the bottom showing the exact query that was executed. This is critical for audit and compliance.

What it shows

The panel displays: Template ID, VQL Query (syntax-highlighted), Execution Time, and Result Count (documents returned before filters).

Example VQL

SELECT id, name, type__v, lifecycle__v, status__v, expiration_date__v
FROM documents__v
WHERE type__v = 'Standard Operating Procedure'
  AND status__v = 'Approved'
  AND is_latest_version__v = true
ORDER BY expiration_date__v ASC

Why it matters

When an auditor asks "What documents did you pull, and how?", you can show them the VQL. There is no ambiguity. You can also copy the VQL and run it directly in Vault's API or native query editor if needed.

Transparency by design: VaultSearch hides nothing. If you want to verify a result, the VQL is there.

Role-Based Access

Roles Overview

VaultSearch supports four primary roles. Your Vault Administrator assigns you one or more roles, and VaultSearch adapts the search experience accordingly.

QA Admin
Full read access to QA-related documents, SOPs, deviations, CAPAs, and audit records.
QA Reviewer / QA Lead
Read access to approved documents and own department's open records.
Clinical Ops
Clinical trial documentation, active holds, clinical SOPs, deviation records, clinical CAPA records.
Regulatory Affairs
Regulatory submissions, approval documents, regulatory dossiers, submission packages.
Validation Engineer
Validation protocols, test results, manufacturing deviations, CAPA documents.

When you open VaultSearch, the suggested query chips adapt to your role. The VQL templates themselves are the same; only the suggested chips and filter defaults change per role.

How Permissions Work

VaultSearch does not manage permissions itself. Instead, it inherits Vault's own Access Control List (ACL).

The session token enforces ACL

When you authenticate with your Vault credentials, a session token is issued scoped to your user account. When VaultSearch runs a VQL query, it includes your session token in the API request. Vault's API evaluates the query against your ACL and returns only documents you are permitted to read.

If you can't see it in Vault, you can't see it in VaultSearch

If you lack read access to a document type in the native Vault UI, VaultSearch will not return it either.

No special VaultSearch permissions needed

You do not need special "VaultSearch permissions" in Vault. Just a standard user account with read access.

Principle: VaultSearch is a UI layer, not a permissions layer. Vault's ACL is the source of truth.

Security & Compliance

Session Token Handling

Session tokens are temporary credentials issued by Vault. VaultSearch handles them securely.

Where tokens are stored

Tokens are stored in the browser's sessionStorage, scoped to the current tab and cleared when the tab is closed. Tokens are never persisted to disk, localStorage, or any server.

Token lifetime

Token lifetime is determined by your Vault instance (typically 1–8 hours). VaultSearch does not control or extend this. When a token expires, you will see "Session expired" and must reconnect via the connect page.

Token scope per tab

Each browser tab has its own independent session. Opening VaultSearch in a new tab requires fresh authentication. Closing a tab clears its token immediately.

Multi-tab security: If you open VaultSearch in two tabs, each tab has a separate token. Logging out in one tab does not affect the other.

Audit Logging

Every search performed in VaultSearch is logged and can be audited. Logs are stored in Vault and are tamper-proof.

What gets logged

For each search: Template ID, Full VQL query, User ID, Timestamp (UTC), Result count, and Any filters applied.

Accessing audit logs

Audit logs are stored in Vault's audit trail. Your Administrator can retrieve them via Vault's Admin > Audit > Query Logs.

CFR 21 Part 11 compliance

The audit logging design respects CFR 21 Part 11 requirements: Every action is logged with user and timestamp, Logs are immutable (stored in Vault's database), Query intent is transparent (full VQL visible), No gaps in coverage (every search is logged).

Audit-ready: You can show an inspector a complete, timestamped log of every search your team ran, with the exact queries and results.

No Data Egress

VaultSearch performs all queries and processing within your Vault instance. No data leaves.

Where queries run

VQL queries execute on Vault's own API servers. Results are returned directly to your browser. VaultSearch has no backend server.

What VaultSearch servers see

VaultSearch has no servers. The only servers involved are: Your Vault instance (API and database) and Your browser and network.

HTTPS encryption

All communication between your browser and Vault is encrypted over HTTPS.

No AI processing

VaultSearch does not use machine learning or external AI services. All query mapping is rule-based and deterministic.

Data sovereignty: Your documents never leave your Vault instance. This is honored by design.

Troubleshooting

I get 0 results

Symptom: A search returns "0 results found," even though matching documents exist in Vault.

Check the filters

The most common cause is an overly narrow filter combination. Example: Searching for "approved SOPs" with lifecycle filter set to "Archived"—no approved SOPs are archived.

Solution: Check the Filters sidebar. Clear filters one by one to see which one is eliminating results.

Review the VQL

Look at the VQL panel at the bottom. The query shows exactly what is being searched. Does it match your intent?

Verify your permissions

If you have no access to a document type due to ACL restrictions, VaultSearch will return 0 results.

Check the Vault instance

Log into Vault directly and manually search. If you find 0 results there too, VaultSearch is working correctly.

Pro tip: Start with a broad search with no filters, then narrow down.

Session expired

Symptom: "Your session has expired. Please reconnect." appears mid-search.

Why this happens

Vault-issued session tokens have a lifetime (typically 1–8 hours).

Solution

Click "Reconnect" or navigate to the connect page. Re-enter your credentials. Your session will be re-established, and you can resume searching.

Extending session lifetime

Contact your Vault Administrator to see if longer token lifetimes are available in your instance.

Field name errors in VQL

Symptom: VQL shows "Field 'status__v' does not exist" or similar error.

Why this happens

VaultSearch templates assume standard Veeva field names. If your Vault instance has custom field names, the templates may reference non-existent fields.

Solution

  1. Note the field name in the error.
  2. Ask your Vault Administrator what the equivalent field is.
  3. Contact VaultSearch support with the field mapping.
  4. Use the native Vault query editor with correct field names in the interim.

Demo vs. Live Mode

Question: What's the difference between the demo and connecting to my actual Vault instance?

Demo mode (demo.html)

The demo is a static, pre-loaded example showing how VaultSearch works. It includes mock data and works without connecting to a real Vault instance.

Live mode (after connecting to Vault)

When you connect to your Vault instance, VaultSearch queries your real documents, respects your real ACLs, and logs all searches.

Transitioning from demo to live

The search UI is identical in both modes. Your muscle memory from the demo applies directly to live.

Recommended flow: Try the demo first, then connect to your Vault sandbox to test, then move to production when confident.

Getting Help

If you encounter issues not covered above:

Check these resources first

  • This documentation — use the sidebar.
  • The demo (demo.html) — compare to isolate whether the issue is VaultSearch or your Vault instance.
  • Vault's native search — test the same query to confirm data exists.

Contact your Vault Administrator

For issues related to credentials, permissions, field names, or Vault configuration, your Administrator can verify your account, check OAuth application settings, confirm field names and custom configurations, and access audit logs.

Report a bug or request a feature

Found a bug? Document it with: The steps to reproduce, What you expected, What actually happened (screenshot/error), Your Vault domain and API version (if safe).
